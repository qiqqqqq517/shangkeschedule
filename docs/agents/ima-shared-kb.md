# 协作规范 · 「上课」项目知识库使用约定

> 面向所有参与「上课 · ShangKeSchedule」开发的人（AI 助手与人类开发者同等适用）。
> 本文的规则与仓库根 `AGENTS.md`「项目记忆与协作规范（IMA 知识库，强制）」节一致；两者冲突时以 `AGENTS.md` 为准。
> 上位事实来源始终是仓库本身（代码 + `工作日志.md`），本知识库是**索引与人读层**。

## 一、两个库的角色（最重要的一条）

| 知识库 | 类型 | 角色 | 允许的写入 |
| --- | --- | --- | --- |
| **上课-共享** | 共享知识库 | **协作主库**：项目记忆的唯一事实入口，所有人看与写都走这里 | ✅ 一切新内容 |
| 上课 | 个人知识库 | **只读备份**：历史快照 + 个人镜像留档 | ⚠️ 仅 `--backup` 镜像；**不再**写入新结论 |

**规则**：

1. 新增、更新、归档项目记忆，**一律写「上课-共享」**。
2. 「上课」个人库只做备份用途，**冲突时以共享库为准**。
3. 不要在个人库里维护「只有自己看得到」的项目结论——那等于把项目记忆变成私有，协作方无法查阅。

## 二、目录结构（8 个一级文件夹，编号固定，不要新增同级）

| 文件夹 | 放什么 | 谁维护 |
| --- | --- | --- |
| `01-总览` | 项目索引、协作规范、DSH 调用指南、待补充清单 | 规则类文档，**改动需在提交里说明** |
| `02-架构与模块` | 架构说明、模块职责、数据结构 | 动架构时更新 |
| `03-运行部署` | 构建、发布、CI、部署口径 | 发版相关改动时更新 |
| `04-接口文档` | 接口契约、数据结构、协议 | 动接口时更新 |
| `05-决策记录` | ADR、方案辩论结论、「为什么这么定」 | **重大决策必写，这是最高频被查的一类** |
| `06-进度与待办` | 当前进度、待办清单、阻塞项 | 每轮收尾更新 |
| `07-问题复盘` | 检查报告、巡检轮次报告、事故复盘 | 自动化产物的默认落点 |
| `08-资料归档` | 外部资料、历史快照、废弃文档 | 只增不删 |

## 三、写入规范（保证「查看方便」的关键）

### 3.1 标题写法

- **能独立表意**：标题脱离正文也能看懂，不要起 `报告.md`、`笔记.md`、`新建文档` 这类名字。
- **带轮次/日期/版本**：`交叉检查报告 · 第 40 轮 · 主题`、`发版记录 · v4.75.14（2026-10-09）`。
- **⚠️ 标题会被截断**：IMA 列表里长标题会被截断（实测截到约 30 余字符，且截断处不带省略号），**关键区分信息必须放在标题前段**。反例：`上课 ShangKeSchedule · 多维度交叉检查报告...`——库里已有多条同名，检索和区分都困难。
- **⚠️ 版本区分信息不能放标题中段**（实测踩过）：笔记命名为 `协作规范 v2 · 「上课」…` 时，IMA **静默丢弃了 ` v2`**，与旧条目变成完全同名。要么直接编进文件名（`协作规范-v2.md`），要么放标题末尾；**入库后必须 `find` 回查一次标题是否被改写**。
- **入库后必做一次 `find <关键词>` 回查**：确认标题按预期落库、且没与既有条目撞名。
- 文件型条目**带扩展名**（`round-40.md`），笔记型条目不带。

### 3.2 正文头三要素（每篇必写）

```markdown
> 取材版本：v4.75.14(518)
> 生成时间：2026-10-10
> 作者：<名字或 Agent 名>
```

作用：别人一眼能判断「这份说的是哪个版本的事」，避免拿过期结论当现状。

### 3.3 只追加，不静默覆盖

- 结论变了 → **追加**一条带日期的更正，写清「原结论 → 新结论 → 依据」，**不要**直接改掉旧结论。
- 追加类操作用 `note-append --marker "<纯文本片段>"`，脚本自带幂等守卫，重跑不会重复追加。
  ⚠️ **marker 必须是「回读形态」的纯文本**，不能抄源 Markdown —— `get_doc_content` 返回归一化纯文本
  （行首 `#` 被剥、`**`/反引号被去、`_` 被转义、`- ` 列表标记归一成 `* `），
  传 `# 一、两个库的角色` 这种 marker 在回读里**永远不存在** ⇒ 守卫恒假放行、正文被追加两遍
  （2026-10-10 实测：3126 → 6252 字符）。脚本现已**主动拒绝**含 Markdown 标记的 marker。
  正确写法：`--marker "一、两个库的角色"`。
- 推翻旧结论时，在新条目里点名被推翻的那条，方便顺着追。

### 3.4 两种写入通道

| 内容形态 | 通道 | 命令 |
| --- | --- | --- |
| 需要长期维护、会被追加更新的文档 | **笔记**（media_type=11） | `node scripts/ima_kb.cjs note-new <标题> <md> --folder 01-总览` |
| 一次性产物（报告、巡检轮次） | **文件上传**（md） | `node scripts/ima_kb.cjs up <文件.md> --folder 07-问题复盘` |

- 文件上传的安全门顺序固定：`preflight → check_repeated_names → create_media → COS 上传 → add_knowledge`，任一步失败立即停止并如实报 `msg`。
- **⚠️ `folder_id` 必须是 `add_knowledge` 的顶层字段**，否则条目会静默落到知识库根目录（实测踩过）。
- 重名不支持覆盖，脚本自动追加时间戳保留副本。

## 四、统一命令（`scripts/ima_kb.cjs`）

先装 ima-skill 并在 `~/.config/ima/` 放好 `client_id` 与 `api_key`
（获取地址 https://ima.qq.com/agent-interface）。

```powershell
# 看有哪些库、共享库结构
node scripts/ima_kb.cjs kb
node scripts/ima_kb.cjs ls
node scripts/ima_kb.cjs ls --folder 07-问题复盘

# 检索与阅读
node scripts/ima_kb.cjs find 交叉检查
node scripts/ima_kb.cjs read <note_id>

# 写入（先 --dry-run 预演，再实写）
node scripts/ima_kb.cjs note-new "标题" .\draft.md --folder 01-总览 --dry-run
node scripts/ima_kb.cjs note-new "标题" .\draft.md --folder 01-总览 --backup
node scripts/ima_kb.cjs note-append <note_id> .\more.md --marker "特征串"

node scripts/ima_kb.cjs up .\report.md --folder 07-问题复盘 --dry-run
node scripts/ima_kb.cjs up .\report.md --folder 07-问题复盘 --backup

# 落库核验（列表命中 + 检索命中 + 阴性对照）
node scripts/ima_kb.cjs verify round-40.md --folder 07-问题复盘
```

`--backup` = 写完共享库后，再往个人库镜像一份。**备份失败不阻断共享库写入**，但会显式告警。

## 五、什么时候必须回写知识库

- 改了**架构 / 数据库结构 / 接口契约** → `02` / `04`。
- 做了**方案选型、踩坑、推翻旧结论** → `05-决策记录`（最高价值，优先写）。
- **每轮工作收尾** → `06-进度与待办`（含下一步可执行的第一步）。
- 出了**问题、事故、检查报告** → `07-问题复盘`。
- **发版完成** → `03-运行部署` 记录版本、校验结论、同步状态。

## 六、纪律

1. **知识库不是代码事实来源**。涉及版本号、数据库结构、文件数量、环境路径这类会随代码变化的结论，**必须回仓库复核**；与代码或 `工作日志.md` 冲突时以后者为准，并把差异回写知识库。
2. **不写死内部 ID**。`knowledge_base_id` / `folder_id` 一律按名称现场解析（`scripts/ima_kb.cjs` 已实现），不要把 ID 抄进文档或脚本常量。
3. **不写死条目数**。内容持续增长，需要盘点时现场跑 `ls`，不要引用历史数字。
4. **不在库里写密钥、签名文件路径凭据、他人隐私信息**。适配网关密钥等**一律不入库**。
5. **写入前先查重**：`find <关键词>` 确认没有同主题条目，避免制造多份同类文档。
6. **IMA 没有删除条目的 OpenAPI 接口**（需要 cookie 鉴权的 `del_knowledge`，凭证调用不了）⇒ **入库前想清楚**，错条目只能人工在客户端删。这是「只追加」成为硬纪律的根本原因。

## 七、已知遗留与 API 限制（2026-10-10 实测）

### 硬限制（无法绕过，只能规避）

1. **IMA 没有删除条目、改标题的 OpenAPI 接口**（删除需 cookie 鉴权的 `del_knowledge`，OpenAPI 凭证调不了）⇒
   **入库前必须 `find` 查重 + 想清楚**；错条目、错标题只能人工在 IMA 客户端处理。这是「只追加」成为硬纪律的根本原因。
2. **⚠️ 笔记标题里的中段文字可能被丢弃**：实测把笔记命名为 `协作规范 v2 · 「上课」项目知识库使用约定`，
   IMA 实际存储为 `协作规范 · 「上课」项目知识库使用约定` —— **` v2` 被吞掉**，与旧条目变成同名。
   ⇒ **版本区分信息必须放在标题最末尾或直接编进文件名**，不要指望中段的 `v2` / `rev2` 会被保留；
   入库后**务必 `find` 回查一次标题是否被改写**。
3. **列表里长标题会被截断**（约 30 余字符，截断处不带省略号）⇒ 关键区分信息放标题前段；
   核验用双向包含匹配，不要假设标题完整。
4. **`search_knowledge` 有索引滞后，核验不能依赖它**：实测刚上传的条目，`get_knowledge_list` 已在目标文件夹内命中、
   `parent_folder_id` 正确，但 `search_knowledge` 命中 0（英文词干更明显）。
   ⇒ **权威判据是「文件夹列表命中」**，检索只作辅助信号；否则上传会被误报失败、诱导重复上传。
   `scripts/ima_kb.cjs verify` 已按此实现（列表命中 + 父目录正确才 `pass`，检索滞后只报 `searchStale`）。
