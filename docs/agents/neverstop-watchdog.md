# 项目巡检与修复流程

> 仅在用户明确要求巡检/持续修复时加载，不因阅读本文件启动任务或创建定时任务。
> 2026-10-15 起替代原「无变化也零间隔全量循环」：默认执行单轮；持续模式按变化验证，避免重复消耗。
> 通用规则、分支/提交授权见 `AGENTS.md` 与 [开发流程](workflow.md)，IMA 见 [协作细则](ima-shared-kb.md)。

## 1. 模式与检查状态

| 模式 | 行为 |
| --- | --- |
| 默认单轮 | 检查 → 在授权范围内修复 → 验证 → 记录，完成即返回结果 |
| 用户明确要求持续巡检 | 首轮按任务范围建立基线；完整基线显式指定；后续仅在输入变化、新失败或深检到期时检查 |
| 用户明确要求定时巡检 | 使用宿主提供的自动化工具创建/更新；每次单轮，不嵌套无限循环 |

- 读取工作日志顶部与相关 IMA，检查 status/分支/worktree。主工作区有他人在途改动时只读报告；需修复则建自有 worktree，不切换他人工作区。
- 首轮记录 `HEAD`、本轮相关已跟踪文件（含未提交变更）的内容指纹、构建配置/依赖/工具链标识、各检查结果与时间到 `build_qa/watchdog/state.json`；后续据此判定变化，不能只看 HEAD 或变更文件名。
- 缓存结果只适用于相同输入；输入不明或结果缺失必须实跑。环境/依赖/检查脚本变化使相关结果失效，不能沿用。
- 持续模式无变化时等待输入/下次检查时点，等待应可被用户打断；不刷「仍正常」消息，不创建重复全绿报告。用户说停立即停止，新指令优先。

## 2. 检查层级

### L0：工作区与授权

按开发流程检查状态与远端，安全快进；只读巡检不改写工作区。红线文件已被跟踪、来源不明的改动、分叉或并行冲突时保留现场并记录，不 reset/rebase 他人工作。

### L1：静态门禁

通过 [统一检查入口](checks.md) 执行，触发范围只维护在脚本中：

```powershell
python scripts/project_checks.py --changed --plan --json
python scripts/project_checks.py --changed
# 用户明确要求全项目巡检，或需要建立完整基线时才运行：
python scripts/project_checks.py --full
```

新增未跟踪文件用 `--files` 明确列出。相关脚本或基线变化会触发对应检查，独立门禁收集完整失败清单；不为无关文档运行 UI/适配扫描。棘轮基线只能在违规净下降时锁定，校验器自身修改须验证应通过/应失败两条路径。不得使用 `--plan` 的结果充当通过。

### L2：编译

明确的完整巡检，或影响 App 的源码/资源/构建输入变化且将提交时，运行三项编译：

```powershell
$env:PYTHONUTF8=1
$env:JAVA_HOME='C:\Program Files\Android\Android Studio\jbr'
.\gradlew.bat :shared:compileKotlinJvm :desktopApp:compileKotlin :androidApp:assembleDebug --console=plain
```

任一失败时记录报错，相关 L3 不跑；纯文档修订按开发流程跳过编译，不能标记「本轮已编译」。

### L3：测试

```powershell
$env:JAVA_HOME='C:\Program Files\Android\Android Studio\jbr'
.\gradlew.bat :shared:testAndroidHostTest :androidApp:testDebugUnitTest --console=plain
```

Android 宿主回归使用 `testAndroidHostTest`；当前另有真实 `jvmTest` 集成回归，桌面数据库/备份等变化时也运行它，两者互不替代。完整巡检时完整跑，一般任务先针对受影响业务回归；共享基础设施/数据库/依赖变化时跑完整相关任务。核对 XML 实际执行，默认复用 Gradle 增量，只有证据指向陈旧产物才 `--rerun-tasks`。

核对 XML 报告中的测试套件/用例确实覆盖预期目标，报告 tests/failures/errors/skipped；无理由缺少预期用例须排查。不能把源码 `@Test` 注解数机械等同执行数（参数化/继承等会不同），也不引用历史固定总数。

### L4：每 4 小时的深检

仅在持续模式到期或用户要求深检时运行，时间从 state 读取，重启不重新计时：

1. 近期提交与工作日志是否对应，当前版本与源码是否一致。
2. 已发布 tag、CHANGELOG、线上版本是否一致；未发布的代码 patch 不强求有 Release。
3. 本轮涉及的文档引用是否可达；不默认扫描全部历史文档。
4. worktree/分支残留仅报告，不清理其他会话。
5. 磁盘低于 5 GB 只报告，不自行删除缓存。
6. 真机覆盖盲区（日历写回、通知、响铃、桌面放置、权限）继续标注未验证。

## 3. 修复与验证

1. 读报错、复现或源码对照，取得根因证据；一次只修一个根因，不顺手添加功能。
2. 先重跑失败项，再按开发流程验证受影响范围。修静态校验器不机械触发所有 App 编译；业务源码提交仍必须三项编译。
3. 同一失败连续 2 次修复未通过即记入 `pending.md`；瞬时网络故障最多重试 3 次（约 20 秒间隔）。OOM 等资源问题冷却后最多再试一次，等待可被打断。
4. 新设计、产品决策、私有适配写入、签名/凭据修改、破坏性操作、需要真机而无设备的链路，停止相关依赖操作，记录缺失条件；可继续无关的只读检查。
5. 普通巡检不修改协作规则、发版流程或远端设置。若本次用户明确授权此类改动，按对应任务流程处理，不能把历史停机条款当成重复确认理由。
6. 日历/通知等真实设备链路未测时不宣称验证完成，也不回滚其他已验证且获授权的改动。

## 4. 授权、收尾与报告

- 「检查/先查找问题」默认仅诊断报告；「巡检并自动修复提交推送」明确授权修复与提交；只授权修复则完成可审阅改动，提交按根规则的认可条件执行。
- 有验证通过的运行时修复时，同批次 bump 一次 patch、更新日志与 IMA、显式暂存并双端推送；具体步骤引用开发流程，不在本文重复。
- 普通巡检不构建/发布正式版、不传夸克、不改发布 tag。CI 构建本身并未被全局禁止，正式发版由独立用户指令触发。
- 有新问题、修复、待办状态变化或实质深检结论时写 `build_qa/watchdog/round-*.md`；无变化只更新本地检查时间。
- 报告按 L0–L4 标记 `PASS/FAIL/SKIP/CACHED`：SKIP 写原因，CACHED 写来源版本/指纹与检查时间，禁止当成本轮实跑。
- 有价值的报告经 `scripts/ima_kb.cjs up … --folder 07-问题复盘` 写共享库；进度仅留摘要和标题引用。全绿无变化不上传，不依赖未入库的历史专用上传脚本。
- 最终答复只列新结论、验证与待办，不复述整轮工具调用。

待办格式：

```markdown
### [YYYY-MM-DD HH:mm] L0–L4 · 标题
- 证据：关键报错、文件、日志位置
- 已尝试：动作与结果
- 缺失条件：设备/决策/权限/外部状态
- 下一步：可执行动作
- 状态：待处理/已解除（时间与版本）
```

## 5. 启动示例（按用户实际意图选择）

- 单轮诊断：「按 docs/agents/neverstop-watchdog.md 检查一轮，先报告问题。」
- 单轮修复：「按该流程检查并修复，验证通过后提交并推送。」
- 持续巡检：「按该流程持续巡检，有输入变化或深检到期再执行；授权修复、提交推送，我说停就停止。」

这些是示例，不构成当前会话或未来会话的自动授权。
